# Wander_Wave: カタログ拡張戦略 — 漫画・本の自動取得と品質判定

## 意図と理由

Wander_Wave のカタログは、現在 Rakuten（本・漫画）、TMDB（映画）、AniList（アニメ）など複数のソースから作品を取得している。しかし、特に **漫画** と **本** のカテゴリが不足している。

- **漫画** — Rakuten だけでは日本の主流作品が中心。海外の漫画（欧米コミック、韓国ウェブトゥーン、グローバル漫画など）が不足。
- **本** — Rakuten の他に国立図書館やその他のソースからも取得したい。

本プロジェクトは：
1. 海外ソース（AniList, MyAnimeList など）から **海外の漫画** を自動取得
2. 国立図書館など日本のソースから **日本の本** を補充
3. **自動判定係** で「日本の作品か、海外の作品か」を判定 → 重複を避ける
4. **監視役** で判定精度を監視し、判定基準を動的に調整
5. **ダッシュボード** で判定結果を表示し、エンジニアが承認/却下

---

## ゴール

- ✅ 海外の漫画を月 200+ 件追加できる体制を整える
- ✅ 国立図書館など複数の本ソースから日本の本を補充
- ✅ 自動判定係で「日本 vs 海外」を 95%+ の精度で判定
- ✅ 監視役が判定エラーを自動検出し、基準を改善
- ✅ ダッシュボードでエンジニアが判定結果を確認・承認できる
- ✅ 毎日自動実行、手動トリガーも可能

## 非ゴール

- リアルタイム取得（毎日朝の決まった時間で十分）
- ユーザーがダッシュボードで編集する（エンジニアのみ確認）
- 自動翻訳（当面は API の日本語フィールドを使う）
- 画像最適化（既存のバックフィル機構を流用）

## アンチゴール

- 判定基準が曖昧で、人間が毎回確認が必要（監視役で改善）
- 判定エラーがカタログに入り込む（承認フローで防止）
- 同じ作品が複数のソースから重複登録される（重複検出ロジック）

## 現在の状況

### 既存のバックフィル機構
- TMDB → 映画・TV ドラマ
- AniList → アニメ
- Rakuten → 本・漫画（日本のみ）
- iTunes → 音楽
- その他 — OpenLibrary, MusicBrainz, NDL（国立図書館）など

### データソースの概要

| ソース | 漫画 | 本 | 日本のみ | グローバル | API | 利用可能性 |
|--------|------|-----|---------|-----------|-----|----------|
| Rakuten | ✓ | ✓ | ✓ | - | REST | 利用中 |
| AniList | ✓ | - | - | ✓ | GraphQL | 新規 |
| MyAnimeList | ✓ | - | - | ✓ | REST | 新規（可能） |
| 国立図書館 | ✓ | ✓ | ✓ | - | REST | 新規 |
| Google Books | - | ✓ | - | ✓ | REST | 検討中 |

### 現在のボトルネック
- Rakuten からの日本漫画は充実しているが、海外漫画がない
- 本カテゴリは Rakuten だけで、マイナー出版や学術書が不足
- 判定係がないので、重複や誤ったデータが混入する可能性

## 実装戦略

### Phase 1: 調査（1-2 日）

各ソースから取得可能なデータサイズを把握。

**タスク：**
1. AniList から漫画を全検索 → 日本 vs 海外の内訳を確認
2. MyAnimeList から同じく確認
3. 国立図書館 API から本データを検索 → 件数、タイムラグ確認
4. Google Books の可用性確認（オプション）

**期待値：**
- AniList: グローバル漫画 5,000+ 件（日本以外）
- MyAnimeList: 同等またはそれ以上
- 国立図書館: 日本の本 100,000+ 件（ただし、Rakuten との重複多い）

**成果物：** 各ソースの概況レポート（データ量、重複率、タイムラグ）

### Phase 2: 自動判定係の実装（2-3 日）

「日本の作品か、海外の作品か」を自動判定するロジック。

**判定基準：**
- **発行国** — 作品の原産国（AniList の `country` フィールド）
- **言語** — 原語（日本語以外なら海外の可能性高い）
- **出版社** — 日本の出版社リスト（Rakuten で既知の出版社なら日本の可能性）
- **Rakuten 重複チェック** — 既存の同名作品があるか

**判定ロジック例（漫画）：**
```
if (country != "Japan" && language != "Japanese") → 海外の漫画 (ACCEPT)
else if (country == "Japan" || language == "Japanese") → 日本の漫画 (REJECT)
else if (title 似たものが Rakuten にある) → 重複 (REJECT)
else → 不確実 (MANUAL_REVIEW)
```

**成果物：** `content-classify` 関数（既存の content-classify を拡張、または新しい関数）

### Phase 3: 監視役の実装（2-3 日）

判定係の精度を監視し、判定基準を動的に改善。

**監視内容：**
1. **日次の判定結果統計** — 承認数、却下数、manual review 数
2. **判定エラー検出** —「日本の漫画と判定されたが、海外だった」など（ユーザーまたは後日の確認から学習）
3. **判定基準の妥当性** — 却下率が急上昇していないか、など
4. **データ品質** — メタデータの不足、異常値検出

**監視ダッシュボード：**
- 過去 7 日間の判定結果グラフ
- エラー率の推移
- 手動レビュー必要な件数
- 判定基準の有効性スコア

**成果物：** `monitor-catalog-quality` 関数 + 監視ダッシュボード

### Phase 4: ダッシュボード実装（1-2 日）

エンジニアが判定結果を確認・承認できるUI。

**機能：**
- 本日の判定結果一覧（ACCEPT / REJECT / MANUAL_REVIEW）
- フィルタリング（メディアタイプ、判定理由、ソース）
- 詳細表示（メタデータ、判定根拠、外部リンク）
- 承認/却下ボタン
- 一括承認（ホワイトリスト）

**データ保存：**
- `catalog_review_log` テーブル
  - id, detected_at, source, type (manga/book), title, decision (accept/reject/manual), judged_by, judged_at, notes

**成果物：** ダッシュボード UI + backend API

### Phase 5: 毎日実行スケジュール（1 日）

Cron で毎日朝に自動実行。

**スケジュール：**
- 08:00 UTC (17:00 JST) — AniList/MyAnimeList から漫画取得 + 判定
- 08:30 UTC — 国立図書館から本取得 + 判定
- 09:00 UTC — 監視役実行 + ダッシュボード更新
- 09:30 UTC — Slack 通知（判定結果サマリー）

**成果物：** Cron 設定 + ドキュメント

---

## 制約

- **API リミット** — AniList/MyAnimeList/国立図書館の API リミットを超えない（1 日 1 回のみ）
- **タイムゾーン** — すべて UTC で記録、ダッシュボードは JST 表示
- **翻訳** — 当面は API の日本語フィールドのみ使用、機械翻訳は Phase 2 以降
- **メタデータ** — 既存の `MOVIES` テーブルのスキーマに合わせる
- **パフォーマンス** — 判定処理は 1 時間以内に完了

---

## 既存との連携

### 既存の `content-classify` 関数
- 現在: 小説・漫画の「表現度」を推定
- 拡張: メタデータ不足時に外部 API で補填

### 既存の `bug-detection` システム
- 判定エラーも「バグ」として検出・可視化
- ダッシュボード統合で一元監視

### 既存の `MOVIES` テーブル
- 新規作品は同じスキーマで `INSERT`
- `source` カラム（既存か新規か追跡）、`reviewed_at` 追加（オプション）

---

## ビルダーに任せる部分

1. **判定基準の精密化** — 発行国・言語の組み合わせロジックをどこまで詳細にするか
2. **監視役の統計指標** — どの数値を監視するのが効果的か
3. **ダッシュボードの UX** — 承認フローの使いやすさ
4. **エラーハンドリング** — API エラー時の復旧戦略
5. **スケーリング** — 大量データ時のパフォーマンス最適化
